## 1. 审查结论

**项目已经具备继续验证的工程基础，但现有计划不足以证明“30/45/60 秒身份一致、成本可控、可交付”的核心目标。建议先完成真实质量与成本验证，再进入通用工作流和商业化。**

最不合理的地方是验收逻辑：把管线接通、mock 成片和原生短视频评测，混用为长视频一致性产品的推进依据。当前更准确的状态应为：**本地单用户工作室已有可运行回路，Harness 已接入并有 mock 验证，真实长片质量与完整成本仍待验收。**

以下基础值得保留：本地单用户范围、三条前台生成路径、已有 provider 分层、磁盘状态与轮询真相、分镜恢复能力，以及真实质量未校准前默认关闭视觉 QC 的做法。暂不需要因为本次审查再次重建 UI 或迁移整套基础设施。

优先级定义：P1 为核心目标验收或真实试用前应处理；P2 为下一版计划应澄清或补齐。这里的优先级不代表已在线上发生事故。

## 2. 逐项意见与证据

### R01：产品目标跨了三个阶段，却没有明确当前只对哪一个负责

**事实：** [PRODUCT.md](../PRODUCT.md) 的用户是创作者本人、本地单用户，成功标准是“愿意每天打开它出片”和仪式感。[计划书 §1](plan.md) 将核心升级为身份一致长视频，随后延伸到 skills/workflows、多供应商、账户和支付。没有明确首个主要用途、可接受制作时间、一次可交付成片的成本，以及何时才需要服务其他用户。

**判断：** 这些方向可以先后成立，但不能共同充当当前 MVP 的完成条件。“竞品难以复刻管线”也是未经对照验证的判断；模块数量本身不能证明质量优势或使用价值。

**建议：** 当前目标收窄为“为创作者本人完成一种明确用途的 30 秒多镜头视频，并能检查、修正和导出”。45/60 秒在同一评测框架下逐档放行；原生短片与图片保留为已实现底座。商业化和通用工作流作为条件触发的后续方向。

**关闭条件：** 计划列出一个主要场景、一个真实任务样例、明确不做项，并记录可交付率、每条可交付片成本、总等待时间和人工返工量。是否每天使用应通过实际使用记录验证，不能由首页审美推导。

### R02：同一份计划含多个互不相容的“现在”

**事实：**

- `docs/plan.md` 顶部和 M2.4 已写 2026-09-05 接入；§2 和 M2.1–M2.3 仍写 orchestrator 恒抛错、30/45/60 不可用或未接 runner。
- M1.1 和 §2 仍写只有 initial commit；实际 HEAD 为 `6c01ba6`，已有 `bb2657f`（M2.4）等业务提交。
- `docs/design.md` §7 的当前说明与 §7.2 的“尚未写入”“orchestrator 仍恒 throw”并存；README 开头仍写完整长视频管线未启用。
- `PRODUCT.md` 要求暗场和钨丝灯；当前 [DESIGN.md](../DESIGN.md) 与项目规则已明确纸色、钴蓝的 Blueprint 方向。

**影响：** 后续执行者可能重复实现已完成模块，或依据旧目标再次重做界面。当前工作区仍有未提交内容，但这不能支持“全部业务代码未提交”的旧结论。

**建议与关闭条件：** 下一版计划统一标明基线日期和 commit；对功能分别记录“已实现 / mock 已验证 / 真实已验证 / 质量已验收”。同步当前目标与设计，把旧审查明确标为历史背景。保留历史内容时增加适用日期或被替代说明，避免继续作为现行指令。

### R03：当前评测不能用于长视频核心目标验收

**事实：** 实际运行 `pnpm run evals:check` 成功，但进一步检查 [prompts.json](../evals/prompts.json) 得到：

| 检查项 | 实测结果 |
| --- | --- |
| 用例数量 | 20 |
| 30/45/60 秒 Harness 用例 | 0 |
| 被引用的独立素材路径 | 7 |
| 在 `evals/` 相对目录或仓库根相对目录可找到的素材 | 0 |
| `evals/runs/` 已存正式运行记录 | 0，仅 `.gitkeep` |

[校验脚本](../scripts/validate-evals.mjs) 检查数量、语言、模式和时长字段，没有验证素材存在，也不执行生成或评分。因此“结构校验成功”只代表输入格式的一部分通过。

**影响：** 五种原生视频模式的短片边界用例有回归价值，却不能证明多镜头身份保持、连接质量和长片恢复。一条真实 30 秒冒烟最多证明该样本链路可执行，不能据此校准可靠的视觉阈值。

**建议与关闭条件：** 保留原生回归集，另建 Harness 评测范围，覆盖 30/45/60、T2V/I2V、tail-chain/extend、人物与非人物、失败重试及中断恢复；先补齐素材及其来源、版本和校验信息。对同一输入做重复生成，并与简单拼接或较少一致性控制的基线盲评。用于定阈值的样本和用于最终报告的样本分开。所有尝试都留档，失败样本不得从分母移除。

这里建议的是评测结构，具体样本数和付费预算仍应写入下一版计划；当前没有证据支持某个样本量已足够。

### R04：“身份一致”的评分规则允许身份完全失败仍达标

**事实：** [rubric.md](../evals/rubric.md) 用五维等权均值乘以 5，单条标准是总分 ≥4.0 且时长、审核通过。按现有公式，`face=0`，其余四项全为 `1`，总分恰好是 `4.0`。

此外，“技术门槛失败不能计入可交付”与最终单条公式不一致：公式没有包括黑帧、冻帧和连接连续性。对于无人物镜头，人工规范也没有单独说明面部、发型和服装如何计分。它还把明显跳切作为连接失败，而计划允许硬切；有意剪辑与错误的连续性断裂需要区分。

**影响：** 通过率可能与“身份一致、可交付”的实际目标不一致；不同评审者也可能使用不同判定规则。

**建议与关闭条件：** 将身份保持和必要技术项设为独立必过条件，风格总分只作补充；人物和非人物分别定义适用维度；按分镜意图区分连续动作与有意换景。至少加入“换脸但光色一致”“首尾正常但中间漂移”“允许的硬切”等反例，并要求统一判定。阈值由对照标注确定，报告自动 QC 的误放和误拒情况。

### R05：当前账面成本不能直接用于验收和定价

**事实：**

- [cost.ts](../src/lib/cost.ts) 的 Harness 预估只累计 generate/extend clip；Director、视觉 QC 等调用不在这项预估中。
- [Director](../src/lib/harness/director.ts) 和 [视觉 QC](../src/lib/harness/visual-qc.ts) 的默认 completer 返回文本，没有将调用 usage 纳入 job 成本。orchestrator 当前按角色表与分镜记录汇总。
- [shot-executor.ts](../src/lib/harness/shot-executor.ts) 在生成完成时以本次返回的 `costUsdActual` 写入 shot 的 `costUsd`；[shot-state.ts](../src/lib/harness/shot-state.ts) 重试仍沿用同一记录，没有每次尝试的累计账目。
- 本次调用真实状态函数，以两次各 `$1.20` 的已计费尝试作为输入，最终 `costUsd` 是 `$1.20`，不是 `$2.40`。这是状态记账路径的最小复现，不是真实供应商账单测试。
- Director 产出后会重写 `costUsdEstimate`（orchestrator 第 151 行附近）；但 rubric 的成本标准使用“提交前预估”。两个基准不能直接混用。

**影响：** 既可能漏计重试和辅助调用，也可能用更新后的预估代替用户提交时看到的预估；因此目前不能可靠证明“≤1.5 倍”，更不能支撑 M4 的账单误差 <1%。

**建议与关闭条件：** 分开保存提交时预估、计划生成后预估、预算上限和实际支出。每次生成、重试、Director、角色表、视觉 QC 都记录独立调用费用；usage 缺失标为未知，不能按零支出处理。内部保留原始精度，仅展示时四舍五入。用成功、QC 拒收后重试、取消和 usage 缺失案例核对完整账目。

本文引用的 `$2.10/30s` 等是仓库估算假设，未认定为当前供应商有效报价；“480p 后高清重打”还会增加一次生成，应计入总成本，也不能假定构图和质量必然复现。

### R06：现有预算检查不足以实现计划中的自动停损

**事实：** [orchestrator.ts](../src/lib/harness/orchestrator.ts) 第 382 行附近的 `assertBudget` 在 `retries === 0` 时直接返回，仅比较已记录支出是否超过当前预估的 2 倍。调用位于 `beforeShot`。

沿 [run-persisted-plan.ts](../src/lib/harness/run-persisted-plan.ts) → [run-persisted-shot.ts](../src/lib/harness/run-persisted-shot.ts) → [shot-executor.ts](../src/lib/harness/shot-executor.ts) 检查：`beforeShot` 在进入分镜执行前调用；同一次执行中的自动重试发生在 `executeShotWithRetries` 内部，不会逐次重新调用该预算钩子。分镜结束后的聚合检查无法阻止已经发出的付费请求。

**判断：** 这是一条未完整落实的执行门禁。即使补上漏记费用，仅检查已经支出的金额也不能防止下一次调用或并行请求突破上限。

**建议与关闭条件：** 在每次付费调用前核对“已花费 + 已预留 + 本次预估”；预留需在并行情况下保持一致，结束后结算。区分质量目标的 1.5 倍与安全停止的 2 倍：前者是验收指标，后者是执行限制，不应互相替代。用临界预算、自动重试、并行分镜及未知费用输入证明不会继续超额提交。

### R07：视觉 QC 的观察范围不足以证明整片一致性

**事实：** [orchestrator.ts](../src/lib/harness/orchestrator.ts) 的 `visualScore` 只抽当前镜头首、尾两帧；参考图来自本镜起始帧及角色表。角色表仅为 R2V 路由涉及的角色生成。T2V/tail-chain 路径不保证始终使用同一份固定身份图作为跨镜参考。

Director 输入当前包含首尾帧是否存在以及参考资产路径，默认请求构造没有把这些图像内容直接传给 Director。其计划不能据此被视为已经理解了上传图片中的具体人物外貌。视觉 QC 默认关闭是已记录的事实，而非本次推断。

**影响（推断）：** 首尾两帧合格仍可能漏掉中间换脸、动作异常；只参考上一镜起点也可能放过逐镜累计漂移。这些是检查覆盖缺口，尚不能据此断言现有真实成片已经出现这些问题。

**建议与关闭条件：** 在评测中明确固定身份参考、镜内抽样、镜间连接及整片检查分别负责什么。增加中段漂移和跨镜累计漂移反例；若仍只检查首尾，应把能力说明限定为首尾抽样检查。将用户输入图、角色描述和生成角色表之间的对应关系纳入人审或自动核验。

### R08：尾帧降级与目标时长需要单独验收

**事实：** 当前 UI 已说明尾帧仅保存，这个边界应保留。[设计书 §7.2](design.md) 把 freeze settle 作为 Grok-only 尾帧策略；[stitch.ts](../src/lib/harness/stitch.ts) 实际从生成片段的末尾抽帧并追加默认 `0.75s` 定格，接口没有接收用户目标尾帧图片。

技术 QC 在拼接前逐镜运行；stitch 返回实际时长，runner 探测后记录成片时长，但相关路径没有按目标对最终完整成片再执行 ±0.4 秒验收。

**判断：** 生成片末帧定格只能作为结束方式，不能验证用户目标尾帧的匹配。若原片已恰好装满 30 秒，再追加 0.75 秒，便与总时长 ±0.4 秒标准冲突；这是可计算的边界案例，不是本次实测成片结果。多镜头各自的时长误差也可能累计。

**建议与关闭条件：** 区分“保存尾帧”“生成片结尾定格”“与用户尾帧匹配”。明确目标时长是否包含定格，拼接后再验证完整成片时长和连接；将该组合纳入真实评测。即梦不可用时，应相应收窄卖点，不能把定格描述为硬锁能力的等价替代。

### R09：M2 已经依赖人审，计划却把可操作的人审放到 M3

**事实：** 分镜重试耗尽进入 `needs_review`，orchestrator 将整个 job 失败。[retryJob](../src/lib/jobs/create.ts) 新建任务并复制 inputs，不继承旧 Harness 计划和已完成分镜。M3 才计划加入 approve 路由与单镜重做 UI。

**影响：** 崩溃续跑与用户点击“重试”是两种能力。当前前者已有库层支持，后者可能重新规划、生成整片。提示“人工复核”却没有相应操作入口，既不能构成质量兜底，也会影响可交付片成本。

**建议与关闭条件：** 将最小分镜复核闭环前移到 M2 收口，不必同时建设通用 workflow 引擎。至少能查看失败原因与已完成分镜、明确选择终止或重做，并说明是否保留成功结果。验证失败镜恢复及其下游依赖如何失效重算，不能只测一条正常 45 秒流程。

### R10：依赖关系与“下一步”顺序冲突

**事实：** M2.0 称即梦 spike 影响 M2.3、必须前置；§6 又称只阻塞 M4、不阻塞 M2.4。M1 标题写“先于一切”，真实 key 冒烟仍未正式验收，M2.4 已推进；§6 把首页收尾排在核心验证之前。

**判断：** 功能探索先行可以接受，但计划需要记录范围调整后的依赖。当前叙述无法回答：缺即梦凭据究竟停哪一项，以及一次真实 30 秒验证通过后还欠哪些验收。

**建议与关闭条件：** 明确当前基线是 Grok-only，即梦验证只阻塞其硬锁承诺和相关扩展；把原生真实冒烟与 Harness 真实验收分开。接下来优先补成本、评测和真实链路证据，首页的非阻断微调按实际影响安排。用门禁条件表达依赖，而不是继续沿用已失真的串行阶段图。

### R11：M3/M4 范围过大，缺少可执行排期和运维验收

**事实：** M3 同时包含技能格式、图执行器、人审与单镜 UI；M4 同时包含新供应商、账户、credits、支付、S3、队列和多实例。验收各自主要是一条流程或出片结果；除早期约一周、spike 一两天外，没有明确工作量、负责人、阻塞处理日期和试验预算。

运行约束也未进入计划验收：文档概括 job 为 15 分钟超时；实际 shot 轮询每次有 15 分钟窗口，启动恢复根据 job 的 `updatedAt` 判断 15 分钟陈旧，并不等价于整片端到端 15 分钟完成。作业并发和每 job 分镜并发是两个层级，尚缺统一上游调用与本地编码资源预算。

**建议与关闭条件：** 将多供应商与商业化拆成独立决策；先以单节点真实运行记录确定完成耗时、超时和恢复策略。每个工作包写明交付证据、依赖、预估工作量区间、费用上限和停止/降级条件。多用户阶段再验收数据隔离、账目一致、重启恢复、持久化和存储保留策略；一次双供应商出片不足以证明可商业运营。

暂不建议仅为远期多实例目标立即迁移 BullMQ/S3。迁移触发条件应来自部署需要和测得的瓶颈。

### R12：门禁结果需要区分“执行通过”与“跳过”

**事实：** [playwright.config.ts](../playwright.config.ts) 允许复用已有开发服务，只有新启动服务时才注入强制 mock 环境。[e2e/lumen.spec.ts](../e2e/lumen.spec.ts) 检查 health 后，会在非 mock 环境跳过测试；该检查确实能避免误消耗额度。交接文档已记录测试复用现有数据目录、CI 未接入，仓库本次也未发现 `.github` 目录。

**影响：** 命令成功退出不必然等于流程被实际测试。共享数据和服务配置还会影响复现；现有绿灯也不能代替真实质量评测。

**建议与关闭条件：** 固定 mock 验证环境，报告实际执行、通过和跳过数量；发布门禁要求关键用例实际执行。为独立运行准备数据目录和服务实例，并验证 Harness 开关关闭、非 mock 环境及恢复场景。将“不消耗额度的功能门禁”和“有预算的真实质量评测”分别记录。
