## 一、战略与计划层的不合理之处

### S1.【高】文档与现实严重漂移 — 设计文档还停留在"仓库没有业务代码"

`architecture.md` rev 3 声称仓库只有 `create-next-app` 脚手架、路径为 `/home/testpc2/Code/VideoPlatFrom`(Linux)。实际情况:

- 仓库在 **Windows** `D:\dev\repos\VideoPlatFrom`;
- PR 1–8 规划的**几乎全部文件已经实现**(providers、runner、HTTP API、SSE、Range、uploads、mock、UI、gallery);
- 实现中新增了文档里**不存在**的东西:`text_to_image` 模式、Sub2API 上游、`src/shaders/warp-field`、`three128` 依赖、`image.jpg` 媒体白名单。

**后果:** 任何按文档施工的人会做重复/冲突的工作;文档里的验收门禁(PR 9)没人执行。
**优化:** 以 as-built 为准重写设计书(见 `docs/design.md`),`architecture.md` 保留为 Phase 0 历史文档。

### S2.【高】全部业务代码未提交 — git 只有一个 initial commit

`git log` 只有 `3038174 Initial commit from Create Next App`,所有业务代码(约 70 个文件)处于未跟踪/未提交状态。一次误操作(checkout、clean)即可全部丢失,也无法按 PR 审查。
**优化:** 立即按模块分批提交(types → lib → api → ui),之后再继续开发。

### S3.【高】harness 是核心产品,但计划里没有它的"产品化"路径

用户定位:「核心是我们研发的 harness 平台」。现文档把 harness 排在 Phase 2,只有 PR 10–13 四行标题,缺:

- **可量化的一致性验收标准**(什么叫"没换脸"?阈值是多少?)
- **金标准评测集**(固定 prompt 套件 + 人工评分表,用于回归)
- **成本模型**(30/45/60 packing 的每条成片预估成本,直接决定商业可行性)
- **shot 级断点续跑**(30s 成片要打 3–5 次 Grok,任何一步失败不能从头重来)

**优化:** 计划书将 Phase 2 细化为 4 个可验收里程碑(M2.1–M2.4),并前置定义 QC 指标与评测集(见 `docs/plan.md` §4)。

### S4.【中】缺"评测/回归"环节

生成型产品改一个 prompt 模板就可能全面回归。当前测试只覆盖纯函数(rest-map、schema、state-machine),没有针对生成质量的固定评测流程。
**优化:** 建 `evals/` 目录:20 条固定 prompt(覆盖 5 模式 + 中英文 + 边界时长),每次 harness 或 prompt 模板变更后跑一遍,人工按 rubric 打分留档。

### S5.【中】鉴权不能等到 Phase 4

原计划"Phase 1 本地单用户、Phase 4 才做账密"在纯官方 key 场景下勉强成立;但实现已加入 **Sub2API 拼车上游**,端口一旦被暴露,消耗的是共享订阅额度,爆炸半径变大。
**优化:** 提前做**最小鉴权**:单个 `LUMEN_ACCESS_TOKEN` 环境变量,所有 `/api/*` 校验 Bearer/Cookie,一天工作量,不等 Phase 4。

### S6.【低】文档内部规则已被实现"合理地"违反,规则本身应修订

- KD 8 的皮肤 registry(`scene/registry.ts` + `skins/placeholder/`)没有实现,取而代之的是 `src/shaders/warp-field` + `SceneHost`。方向没问题,但设计规则与现实不一致;
- 媒体白名单从 `{video.mp4, poster.jpg}` 扩为含 `image.jpg`(t2i 需要,合理);
- `JobPublic.output` 从平面结构改为 `kind` 判别联合(合理)。

**优化:** 在设计书中按 as-built 修订这些约定,而不是让代码继续背离文档。

## 二、实现层缺陷(按严重度)

### C1.【高】源视频 data URI 兜底 — 违反自身红线,且必然出事

设计文档明确:源视频**不用 data URI**(48MB 上限走 Files API)。但实现:

- `runner.ts` L137:Files 上传失败时降级 `"sending source video as data URI"`;
- `native.ts` `toSendableVideo()`:把整个 mp4 读入内存并 base64 → 48MB 视频变 **~64MB JSON body**,大概率被上游 413/超时,还会撑爆内存。

**优化:** Files 失败即 fail job,错误文案「源视频上传失败,请重试」;如要保留兜底,仅允许 ≤2MB 的源片走 data URI。

### C2.【高】Windows 构建会丢 ffmpeg 二进制

`next.config.ts`:

```ts
outputFileTracingIncludes: { "/*": ["./node_modules/ffmpeg-static/ffmpeg"] }
```

Windows 下二进制名是 `ffmpeg.exe`,tracing 匹配不到 → `next build` 后 `next start` 无法出 mock 片/poster。开发模式(`next dev`)不受影响,所以现在没暴露。
**优化:** 改为 `"./node_modules/ffmpeg-static/ffmpeg*"`(glob 同时覆盖 Linux/Windows)。

### C3.【中】`uploadId` 路径穿越

`create.ts` `loadSidecar()` / `claim()` 直接 `path.join(tmpDir(), uploadId)`,而 `uploadId` 来自请求体,未做格式校验。`"..\\..\\foo"` 可读取 data 目录外的 `.json`、`rename` 任意文件。media 路由的 `jobId` 有 `assertSafeId` 保护,upload 这条线漏了。
**优化:** `createJobBodySchema` 中各 uploadId 加 `z.string().regex(/^up_[0-9a-f]{16}$/)`,或在 `loadSidecar` 入口 `assertSafeId(uploadId)`。

### C4.【中】双份 three.js 进 bundle

`package.json` 同时有 `three@^0.185.1` 和 `three128: npm:three@0.128.0`(warp-field 皮肤抄自旧 demo),外加 `three128.d.ts` 类型 hack。两份 three 各 ~600KB min,纯浪费,且两版 API 混用是长期地雷。
**优化:** 把 warp-field 渲染器移植到 three 0.185,删除 `three128` 与类型 hack。

### C5.【中】Range 实现不符合 RFC 7233 的 suffix 形式

`media/[jobId]/[file]/route.ts`:`bytes=-500`(最后 500 字节)被解析成 `start=0, end=500`,返回的是**开头** 501 字节;416 响应也缺 `Content-Range: bytes */{size}`。Safari 恢复播放时常发 suffix range。
**优化:** 单独处理 `m[1] === ""` 分支:`start = size - Number(m[2]); end = size - 1`。

### C6.【低】取消后仍写入 `outputs/`

设计要求:cancel 后 xAI 即使返回 done 也「不得写入 outputs/」。实现 `persist()` 是**先下载写盘、后检查 canceled**,状态虽保持 canceled,但字节已落在 `outputs/video.mp4`。
**优化:** 下载到 `data/tmp/` 再检查状态后 rename;或 persist 前先读一次状态。

### C7.【低】boot recover 把排队久的 queued 任务错误标为 expired

`recover()` 对 `updatedAt` 超过 15 分钟的 `queued` 任务直接 `fail(id, "expired", "任务超时")`。排队久不是错误(比如队列里排了 20 个);且 `fail()` 内部只对 `pending` 状态给 `expired`,queued 会落成 `status=failed, code=expired`,语义混乱。
**优化:** 15 分钟超时只适用于 `submitting/pending/persisting`;`queued` 一律重新入队。

### C8.【低】SSE 缺心跳与断连清理

`events/route.ts` 没有设计要求的每 15s `: ping` 心跳(代理/浏览器会掐空闲连接);客户端中途断开时监听器不释放(只在终态 `off()`),长期运行会积累泄漏。
**优化:** `setInterval(15s)` 心跳 + `request.signal.addEventListener("abort", off)`。

### C9.【低】上传超限后残留 tmp 字节

`upload.ts` 视频超 48MB 时 `ws.destroy()`,已写入的字节留在 `data/tmp/{id}`,只能等 24h sweep。可接受,但主动 `rm` 更干净。图片分支整图入内存(≤12MB)与"流式"原则略有出入,量级可接受,不强制改。

### C10.【低】`fail()` 时 xAI file 删除是 fire-and-forget 且仅在 fail 路径

取消(cancel)路径没有删 `xaiFileId`(设计说 cancel 后尽力 DELETE)。核对 cancel 路由是否处理;若没有,补上。

## 三、设计层可优化点(harness 相关,影响 Phase 2)

### H1. tail-chain 抽帧应避开运动模糊帧

设计只说"抽上一镜最后一帧"。真实视频最后一帧常是运动模糊/过渡帧,直接当下一镜首帧会放大不一致。
**优化:** 在最后 0.5s 内抽 12 帧,按拉普拉斯方差(清晰度)选最优帧作为链接帧。

### H2. QC 打分需要校准,不能拍一个 0.6 阈值

`grok-4.6` 视觉打分 0–1、阈值 0.6 是拍脑袋值。**优化:** 用评测集先跑 30 组「同人/不同人」对照,画分布后再定阈值;rubric 固定为:面部、发型、服装、光线、色调五项各 0–1,取加权。

### H3. 多 shot 并行化与 shot 级断点

30s 成片 = 3–5 次 Grok 调用、3–10 分钟。设计没写并行策略与断点。
**优化:** 无依赖的 shot(keyframe-cut 段)并行提交(受 `JOB_CONCURRENCY` 约束);`job.json` 增加 `shots[i].status/remoteId/outputPath`,失败从失败 shot 恢复,不重打前面已成功的 clip。

### H4. harness 成本模型缺失

按平坦价:30s hybrid(15gen+10ext+5gen)≈ 15×0.08+10×0.05+5×0.08 = **$2.10**;60s ≈ $4.20;QC 重试 ×1.5 系数后 30s 实际约 $3。这决定定价与重试预算,必须进 `cost.ts` 与提交前 UI 预估。

### H5. 即梦(Jimeng)风险敞口应显式化

尾帧硬锁完全依赖即梦/Seedance 的 `first_tail` 能力,而该 API 形状标注"未核实"。若不可用,产品的"尾帧锁定"卖点只剩 freeze settle。
**优化:** 在 Phase 2 早期(而非 PR 15)先做一次**一天的 spike**验证即梦 API 可用性与效果,再决定 packing 策略,避免 Phase 2 后期才发现地基不存在。
