### 1.2 结构性问题

**A1.【高】前端形态与产品目标错位**

`PRODUCT.md` 定义的成功 = "创作者愿意每天打开它出片"。旧 UI 是"左边一个装饰性 WebGL 舞台 + 右边一张 6 段表单"，出片后要滚到页面下方看进度，再滚到更下方的画廊找成片。信息流是**表单 → 监控 → 画廊**三段式，每次生成都在重新填表。

对创作者来说，出片是一次连续的对话：说一句、看结果、改一句、再看。Agent 会话结构（历史在左、对话流在中、输入框在底）把"提示词 → 进度 → 成片 → 再提示"压成一条线，并天然支持"复用提示词 / 重试 / 取消"这些高频动作。**本次已重构为该结构**（见第三节）。

**A2.【高】单进程 in-memory runner 是上限，也是当前最大的稳定性风险**

`JobRunner` 与 SSE EventEmitter 同 isolate、内存队列。任何一次 `next dev` 重编译或进程重启都依赖 boot recover 兜底，且无法水平扩展。Phase 1 可接受，但 Harness 30s 成片一个 job 要打 3 到 5 次 Grok、跑 3 到 10 分钟，进程重启的概率显著上升。

建议路线（按 `docs/plan.md` M4 提前一档）：

1. 先把 `runner.ts` 内部的"取任务 / 执行 / 写状态"切成 `Queue` 接口（`enqueue / claim / ack / fail`），现有实现改名 `InProcessQueue`；
2. 加 `BullMQ + Redis` 实现同一接口，`QUEUE_DRIVER=inprocess|bullmq` 切换；
3. SSE 改为订阅 Redis pub/sub 或直接以 2s 轮询为唯一通道（当前设计已经允许）。

**A3.【中】前端状态所有权分散，UI 组件直接 fetch**

旧 `GenerateForm` / `JobProgress` / `HealthStatus` 各自 `fetch("/api/...")`，401 处理、错误文案、幂等 key 散落。本次抽出 `src/lib/client/jobs.ts`（API 封装）与 `useJobLive`（SSE + 轮询 hook），组件只处理展示。后续加 Harness 状态、人审门时只改这一层。

**A4.【中】无 E2E / 视觉回归**

单测只覆盖纯函数；UI 改动完全靠人眼。建议加 Playwright（mock 模式下）跑 3 条冒烟：空态、提交文生图并等待完成、失败后重试。截图入 `evals/ui/`。

**A5.【低】死代码**

`src/shaders/animated-top-dock`、`src/shaders/warp-field`、`threeui.css`（40KB）、`fragment-mono.woff2` 无任何引用，且被 eslint 显式忽略；`.impeccable/` 是上一轮设计工具残留。**已删除**。

**A6.【低】Harness 状态未进公开 DTO**

`JobPublic.harness = { enabled: false }`、`bible/shots = null` 字面量。放开 30/45/60 时前端需要 shot 级进度（每镜状态 / 重试次数 / 当前成本）。建议在 M2.4 同时定义 `JobPublic.harness = { enabled: true, shots: ShotPublic[], costUsdSoFar }`，会话页里的助手轮已经预留了"阶段列表"位置可直接扩展为镜头列表。

### 1.3 推荐的稳定架构（目标态）

```
浏览器
  SessionShell(状态所有者) ─ Thread/Turn(展示) ─ Composer(输入)
        │  lib/client/jobs.ts + useJobLive      (唯一 API 边界)
Next.js Route Handlers  (Zod 校验 / 鉴权 / 幂等)
        │
Queue 接口  ── InProcessQueue(现在) ── BullMQ(Redis, M4)
        │
JobRunner ── ProviderRouter ── GrokNativeProvider / MockProvider / JimengProvider
        │             └── HarnessOrchestrator(Director → Keyframe → Shots → QC → Stitch)
MediaStore 接口 ── LocalFs(现在) ── S3(M4)
```

原则：**接口先行、实现可替换、磁盘是真相、UI 不做防线**。这四条当前后端已经做到，前端本次补齐。

### 1.4 能吸引用户的设计要点（产品层）

1. **对话即工作流。** 一条线里完成提示、看进度、拿成片、复用、重试。不需要学习"模式矩阵"。
2. **结果永远最亮。** 背景与 chrome 保持低亮度，成片是屏幕上唯一高对比的东西。
3. **状态有身体。** 背景光流随任务状态变化（待机慢流、生成中变亮变快、完成一次暖光、失败偏冷），不看数字也知道在忙。
4. **费用前置。** 每次提交前显示预估，完成后显示实际；这是烧额度产品的信任基础。
5. **诚实的边界。** 30/45/60 秒在选项里可见但禁用并注明原因；尾帧标注"仅保存，不锁定"。不制造期待落空。
6. **下一步动作就在结果旁。** 复用提示词、下载、重试贴着成片；后续 Harness 放开后加"以此为首帧继续""延长这段"。

## 三、本次重构（as-built）

### 3.1 结构

```
src/components/agent/
  SessionShell.tsx   状态所有者：jobs、侧栏、聚焦、预填、鉴权、背景状态
  Sidebar.tsx        记录（按日期分组、全部/图像/视频筛选）+ 健康/上游状态
  Thread.tsx         空态（问候 + 4 条示例）或 Turn 列表
  Turn.tsx           用户轮（提示词 + 参数 chips）+ 助手轮（进度 / 成片 / 错误 / 动作）
  Composer.tsx       模式 chips、自增高输入、附件、参数、成本、发送
  Backdrop.tsx       R3F 全屏 GLSL 光流，状态驱动；WebGL 失败回落 CSS 渐变
  labels.ts          文案与状态映射
src/lib/client/
  jobs.ts            uploadFile / createJob / cancelJob / retryJob / 幂等 key
  useJobLive.ts      SSE + 2s 轮询，终态自动停止
```

删除：`components/studio/*`、`components/scene/*`、`shell/StudioShell.tsx`、`shell/JobDetailProgress.tsx`、`src/shaders/*`、`.impeccable/`。

### 3.2 保留的行为

- 全部 API 调用、请求体构造、每模式校验文案、幂等 key 保持与旧实现一致；
- 尾帧仍"仅保存"；30/45/60 仍可见禁用；R2V 1080p 禁用；
- SSE 用于反馈、轮询为真相；401 弹访问令牌对话框；
- WebGL 失败不影响表单；`prefers-reduced-motion` 下背景静止、动画归零。

### 3.3 设计规格

见 `DESIGN.md`（已按新系统重写）。要点：暗底 `#0B0B0D`、钨丝金 `#E6A34B` 单一强调色、Geist + 系统中文字体、圆角三档（chips 全圆 / 控件 10px / 面板 18px）、图标统一 Phosphor。

### 3.4 验证

- `tsc --noEmit`、`pnpm lint`、`pnpm test`（145）全绿；`pnpm build` 通过；
- mock 模式下提交文生图（3:4）与文生视频（15s / 1080p），会话流正确追加、自动贴底、完成后展示媒体、费用、下载与复用。
