# Genius 反向评审：已实现能力的失败边界

日期：2026-09-08。源码基线：`43873a7c90e51ca058f623281e0cae0fc483f887`。
状态：审查交付，未修业务代码。配套实施建议见 `plan-unimplemented-2026-09-08.md`。

## 1. 结论与证据边界

优先修复资金和付费请求的恢复语义，再扩大画布、长视频与支付。现有功能数量已足够支撑内测；继续增加入口并不能解决用户遇到断网、跨期、失败后“不知道花了多少钱、该不该再点一次”的问题。

本次覆盖计费/订阅/用户、Agent、Jobs/Provider/Harness、媒体、前端关键路径、部署备份脚本和计划文档。不是逐行形式化证明，也不代表未列出的模块没有问题。

- **运行复现**：子审查在隔离临时 DATA_DIR 中调用真实 TypeScript 函数，通过注入失败 completer、写盘失败和时钟边界复现 R01–R05。没有调用付费上游、读取密钥或修改生产数据。临时探针未作为永久测试提交；下文给出可转成回归测试的步骤与观察值。
- **代码确认**：R06–R13 有明确控制流证据；未在生产制造断网、崩溃或故障。涉及上游是否实际受理的描述均是触发前提，不声称已经造成线上损失。
- **线上边界**：Computer Use 三次未通过 URL 识别检查。只能确认 Chrome 标题为“登录 · Genius”，没有成功读取业务页面，更没有验证生产部署等于本地 HEAD。
- **现有验证**：Grok client / Kling client / retry-guard 的 3 文件 25 测试通过；其中 Grok 测试明确要求 POST 503 后重发，证明现有测试也可能固化错误语义。`pnpm evals:check` 退出 1，缺 `evals/assets/character-en.jpg` 与 `character-zh.jpg`，涉及人物一致性样本。
- **本轮完整单测基线**：`pnpm test` 实际通过 90 个文件、1036 条测试，1 条跳过（约 61 秒）。这说明已有回归绿，不证明本文列出的故障窗口已有覆盖。仅新增文档，未改业务代码，未重跑 UI e2e，也未声称线上验收完成。
- 工作区原有旧设计包删除、新设计包与 `.codex/` 未跟踪内容保持原样。本轮新增两份文档，不提交、不部署。

优先级：P1 = 应在扩大真实付费使用前修复；P2 = 有条件触发的可靠性或明确用户体验问题。没有认定 P0，也不把所有已知限制升级成漏洞。

## 2. Review 指摘

### R01 · P1 · 余额与幂等凭据不是一次原子提交【运行复现】

**位置**：`src/lib/billing/ledger.ts:183`（writeUser）、`:184`（appendLedger）、`:158` 起的去重判定。

先更新余额再写流水，而下一次是否重复扣款/充值却依赖流水。余额写成功、append 失败或进程退出后，下一次同 jobId/ref 会被当成首次执行。这不只是“对账少一条”，会影响实际余额。

**复现**：隔离用户余额 ¥10，将该用户流水目标暂设为目录使 append 抛 EISDIR；执行同一 jobId 的 ¥1 扣款，函数报错但余额已变 ¥9；恢复流水可写后同 jobId 重试，余额变 ¥8。

**建议**：余额与 operationId 的已应用标记必须同一原子状态提交，流水作为可恢复导出；或放入同一数据库事务。仅交换两次写入顺序会把故障换成“有流水却未改余额”，不能解决。保留唯一 applyBalanceChange 入口。

**验收**：在每一写入边界注入失败并重启，同一 operation 最多改变余额一次；余额与流水可确定性恢复。扣款、礼品码、订阅发放、退款都覆盖。

### R02 · P1 · 智能体退款把会员积分转成已购余额【运行复现】

**位置**：`src/lib/agent/run-turn.ts:109`、`:173`；`src/lib/billing/ledger.ts:95` 起的分池逻辑。

对话默认先扣会员池，失败退款为默认正 delta，进入已购池。绕开“会员积分不能用来购买订阅”的产品硬约束。

**复现**：有效会员，已购 ¥0、会员 ¥1；向真实 runTurn 注入总失败的 completer，结束后已购 ¥0.05、会员 ¥0.95。没有真实上游调用。触发依赖 LLM 整体失败；不能据此断言任意用户能无限主动套利。

**建议**：退款关联原 charge 的分池快照，原路退回；会员部分保留原订阅/期次归属，过期后也不能转成永久已购余额。沿用原退款 ref 和唯一资金入口，记录 refund_pending 以便补偿。

**验收**：全会员、全已购、混合支付、跨期/到期后退款及重复退款。

### R03 · P1 · 订阅购买与生成任务准入不互斥【运行复现】

**位置**：`src/lib/billing/subscription.ts:307`、`:350`；`src/lib/jobs/create.ts:293`；`src/lib/agent/run-turn.ts:108`。

任务在 admission 锁内检查余额并随后写任务；订阅仅持 user 锁。即使订阅会减去已经存在的任务预留，也看不到“已通过准入但还未写入”的任务。

**复现**：保持 admission 临界区与已通过的余额检查，调用 purchaseSubscription 仍可完成。隔离夹具中已批准任务价 ¥406.8，订阅完成后可用金额仅 ¥22；任务继续落盘即超额承诺。金额是探针输入，不是生产价格。

**建议**：所有会减少可用资金的购买入口遵守 admission → user；检查和形成资金承诺在同一临界区。不能在已持 user 锁时回头拿 admission 锁。

**验收**：用 barrier 固定两请求交错顺序；任务/订阅/对话同时提交也不能消费同一可用额度。

### R04 · P1 · 已扣款但订阅未落盘时，余额刚够的用户无法补建【运行复现】

**位置**：`src/lib/billing/subscription.ts:329`、`:351`。

代码识别 charged=true 且首期未发放的恢复场景，却继续要求当前余额 ≥ 订阅原价。用户已经付掉的钱被再次作为准入条件。

**复现**：余额恰好为真实函数算出的标准月费；留下一条合法 sub:key 扣款，模拟写 subscription 前中断；同 key 重试得到 insufficient_balance，subscription 仍为空。现有高余额恢复测试未覆盖这个边界。

**建议**：先恢复已支付订单，按原订单快照补履约，不再执行首次购买余额检查。必须保存原 plan/cycle/price/requestHash，禁止同 key 改参数补建另一档；也不能使用当前价重算历史成交金额。

**验收**：扣款后余额为 0、价格已变、同 key 异参、已到期旧 key，分别得到原订单恢复或明确冲突，不重新收费/续期。

### R05 · P1 · 年付跨 30 天期后，旧期积分仍可先被花掉【运行复现】

**位置**：`src/lib/users/schema.ts:74`、`:88`；`src/lib/billing/admission.ts:66`；`src/lib/billing/ledger.ts:212`；`src/lib/billing/subscription.ts:209`。

可用会员池只验证总 expiresAt，没有验证 periodIndex 已切到当前期。跨期结算依赖 GET /me 或 /subscription；直接提交 API 或页面长期开着时，顺序不保证。

**复现**：年付用户第 31 天，尚未触发读取结算，旧期 ¥12 被 assertBalance 放行并扣光；随后 settle 又发本期和当日积分 ¥12.6。旧期本应先清零。整份订阅到期已有保护，本问题专指年付中间期。

**建议**：准入和资金变动前，在正确锁序内完成当前期结算；读 API 不应决定资金规则何时生效。在途任务须有明确的期次预留，避免生成跨期后临时转扣已购池。

**验收**：不先 GET、时钟跨期、跨期在途任务、重复结算、过期退款与进程恢复。

### R06 · P1 · 付费提交结果未知，被当作可重试失败【代码确认＋现有测试】

**位置**：`src/lib/providers/grok/client.ts:21`、`:58`、`:73`；`src/lib/jobs/runner.ts:570`；`src/lib/jobs/retry-guard.ts:64`；`src/lib/harness/shot-executor.ts:61`、`:215`。

两层同类问题：

1. Grok POST 默认最多 3 次，超时/5xx 可重发；现有 `grok/client.test.ts:75` 断言视频 POST 503 后调用两次。根据交接文档生产未配 Grok，所以这是启用门禁，不能写成当前生产事故。
2. Kling/YMan 虽已设置 maxAttempts:1，但“已受理、响应丢失”在运行期被落成普通 failed；一键重试只拦 uncertain_submit。Harness 普通 submit 异常还可能由业务层自动重试。启动时的崩溃保护没有覆盖进程仍存活的网络失败。

**建议**：provider 统一区分明确拒绝、已接受、结果未知。只有明确未受理才允许新 submit；未知先查单，不支持查单则等待核验。已有 remoteId 的轮询/下载失败恢复原阶段，不能重新买一条片。免费 GET 重试保留。

**验收**：假上游先记一单再断开响应，自动恢复/用户重试/重启后仍最多一单；参数被明确拒绝仍可正常修改后重试。

### R07 · P1 · Job 已落盘、幂等映射未落盘时，同 key 可再创建一单【代码确认】

**位置**：`src/lib/jobs/create.ts:293`、`:294`；`src/lib/jobs/idempotency.ts:8`、`:21`。

任务记录与映射是两次写入，JobRecord 不保存可重建映射的 key/hash。崩在中间，runner 启动恢复原 queued 任务，客户端同 key 重试查不到映射，又建一单。映射使用普通 writeFile，读失败统一 miss 也会放大问题。

**建议**：owner + keyHash + requestHash 随任务事实源原子保存；映射变为可重建索引。索引失效时先恢复再处理新创建；不能只把映射改成 rename 就声称跨文件原子。保留有效期策略并区分数据损坏与 key 不存在。

**验收**：每个写入边界 crash/restart 后同 key 返回同 jobId；同 key 异参 409；不同 owner 不串单。

### R08 · P1 · Agent 的内部轮次幂等不能覆盖 HTTP 重放【代码确认】

**位置**：`src/lib/agent/schema.ts:122`；`src/lib/agent/run-turn.ts:101`、`:109`、`:212`。

请求没有 clientTurnId，每次调用随机 turnId。服务端成功而响应丢失后，重发相同用户消息生成新 turnId，既再次收对话费，也可能新建生成任务。agent:<turnId> 仅保护同一轮内部，不能保护浏览器重发。

**建议**：持久化 owner + session + clientTurnId + requestHash；执行前落轮次状态，重放查询原结果；失败消息允许查询、重试、编辑。用户主动再次创作用新 key，不能按文本相等粗暴去重。

**验收**：丢回包、双击、刷新、进程退出后同 key 的 charge 和 action jobIds 都不增加。

### R09 · P2 · 上游超时不覆盖响应体和成片下载【代码确认】

**位置**：`src/lib/providers/grok/client.ts:64`、`:82`；`src/lib/media/persist.ts:22`。

fetch 返回响应头即清除 timer，随后 res.json()/pipeline 不受这个截止时间约束。200 后 body 停滞可长期占用 runner 并发槽；取消写状态不能终止下载。底层网络库可能另有超时，因此不声称永久挂死。

**建议**：期限覆盖 body 读完、落盘结束；下载有总期限和空闲期限，取消传递 AbortSignal 并清理半成品。下载失败保留 remoteId，配合 R06 恢复原产物。

**验收**：响应头立即发出、body 停滞的本地假服务器；期限内中断并释放槽位，排队任务继续运行。

### R10 · P2 · 历史会话续聊被当前页面配置静默覆盖【代码确认】

**位置**：`src/components/genius/agent/AgentView.tsx:128`、`:191`；`src/lib/agent/run-turn.ts:87`。

打开历史仅 setSession，未恢复 tier/skill/products，续聊 body 却使用页面选择。选 B 技能后打开 A 会话，下一轮会静默应用 B；刷新再打开 quality 会话可能落到默认 balanced。产品值为空时服务端可回落历史，不能泛称所有会话配置都丢失。

**建议/验收**：选择与会话绑定，明确显示当前配置；A/B 会话切换和刷新后续聊保持原设置，用户显式改动才覆盖。

### R11 · P2 · 续轮请求失败后提示词从输入框消失【代码确认】

**位置**：`src/components/genius/agent/AgentChat.tsx:85`；`src/components/genius/agent/AgentView.tsx:180`。

发送前清 draft，失败后 finally 又清 pendingText，用户无法原文重试。余额不足等未被服务端保存的失败会丢长输入。

**建议/验收**：保留 failed outgoing message 和编辑/重试入口；明确成功才清草稿。响应未知先按 R08 查轮次，防止“恢复草稿”反而诱发重复收费。

### R12 · P2 · 画布原型的产品边界没有告知用户【代码确认】

**位置**：`src/components/genius/canvas/CanvasView.tsx:113`、`:185`、`:518`。

输入与模型选择看起来可真实生成，还有积分显示，但结果由 1.6 秒定时器置 done，状态仅在组件中，离页即丢。原型尚未实装是已知范围；生产用户缺少“演示、不保存、不扣费”的可见说明才是本条问题。

**建议/验收**：近期明确标识演示和示例结果，避免真实计费暗示；之后分阶段做文档保存和单节点真生成。中英文用户都能在首次操作前知道边界，无需立即实现整套工作流。

### R13 · P1 · 自动回滚仅覆盖健康检查分支，不能覆盖完整部署失败【代码确认】

**位置**：`scripts/deploy.sh:108`、`:115`、`:118`、`:149`。

先停服务再原地解包/装依赖/补别名；这些准备步骤失败可能在进入健康检查之前退出，旧服务不自动恢复。另外回滚只换回 .next，已经覆盖的 package/config/node_modules 不一起回滚，依赖变化的发布可能无法用旧构建启动。`echo "$(pnpm install ... )"` 也不可靠传播安装退出码。

**建议**：独立 release 目录先准备依赖并核验；完整版本包含构建、依赖、配置，data/env 外置。短暂停机切换，错误处理统一恢复旧 release 并验证；迁移必须标可逆性。未在生产故障注入，不声称现有版本已因此停机。

**验收**：隔离演练解包失败、依赖失败、启动失败、健康失败，均能启动完整旧版本且部署命令非零。

## 3. 不应作为缺陷的既有取舍

| 既有实现/取舍 | 本次判断 |
| --- | --- |
| 单机文件存储、进程内队列 | 内测合理；真正问题是事务/恢复边界，不能用“换数据库/Redis”一句话代替诊断 |
| index.json 为派生缓存，job.json 为事实源 | 合理；恢复路径需健全，不要求倒回全表扫描 |
| Origin/Referer 都缺失时放行 | 已授权的非浏览器客户端取舍，不作为本次 CSRF 漏洞提出 |
| 私有媒体 private,no-cache 和 owner 校验 | 正确；不建议为了缓存命中改成 immutable |
| 失败不向用户收费、付费 POST 尽量不重发 | 产品政策合理；上游损失由平台承担需计量，不等于应该强行改成失败扣款 |
| 无支付、没有开放全部视频模式、关闭 Harness | 内测范围与质量门禁合理；不能把“配置了 key”当成能力质量验收 |
| 单语言服务端错误、会话留存未做、CLI 无跨进程锁 | 已知未做仍需排期，但不要伪装成新发现。CLI 应迁到同一写入入口，见计划 |

## 4. 建设性的不同建议

1. **把“恢复一次已付费生成”排在新增模型前面。** 增加查单、续下载、结算待处理和用户可理解的状态，比单纯增加模型目录更能降低重复消费与人工支持。
2. **Agent 的价值从“自动下单”转向“可审阅的创作提案”。** 当前历史只传文本，不能可靠引用上一张资产做保主体修改（run-turn.ts:255）；先补素材引用与执行报价，再扩大自主执行范围。普通文本追问仍然有效，不否定现有对话功能。
3. **画布先解决保存与复用，再做复杂图执行。** 单节点能刷新恢复、产物能回到作品库，就是可交付增量；一次做无限画布、多人协作、音频工具会拖延真实闭环。
4. **订阅卖可解释的权益与期限。** 现行年付是 12×30=360 天，日积分为访问触发，不应默认写成自然年或离线补发。`plans.ts:123` 的价格公式已包含 30 天日赠积分，不能指摘为漏算；但成本比只采默认视频/图片产品，是否覆盖全部可选产品的实际成本仍需压力测算。本轮未据此认定亏损，因为未核实生产实际成本。
5. **备份验收改为恢复演练。** backup.sh 活库分别读 users/ledger/gift-codes，不提供跨文件一致快照；tar 可读不等于账目同一时点。作为需要演练的风险登记，不声称现有备份已损坏；同机备份也不能证明异地灾备有效。
6. **文档事实源需要校准。** handoff 基线仍写 c8ee230/干净，与本次 HEAD/工作区不符；模板落种已在 deploy.sh 自动处理，交接仍写必须手动。DESIGN front matter 仍将 Agent/订阅称为本地交互。建议实现批次收尾时统一核对 as-built；历史计划正文保留，顶部只标状态。

## 5. 修复顺序

先 R01–R05（资金事务/池/期次）→ R06–R08（付费请求与客户端幂等）→ R13（可恢复部署）。R09–R12 可并行作为独立模块工作，但必须避免多人同时改资金内核。

以上是审查和设计建议，不表示用户已批准任何架构迁移、付费实测或生产变更。未实装能力的契约、里程碑和验收见配套计划。
